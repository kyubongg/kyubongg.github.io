> 에이전트로 바꿨다. #1 마지막에 "실제로 정리를 맡겨본 결과를 다루겠다"고 썼는데,
> 그 결과가 생각과 많이 달랐다.

## 왜 바꾸려 했나

빌드로그 #1에서 만든 FileButler는 **워크플로**였다. 흐름이 코드에 박혀 있었다.

```
파일 읽기 → LLM 호출 1회 → 분류 결과 받기 → 코드가 이동
```

LLM은 한 번 불리고 끝났다. 무엇을 더 볼지, 정보가 부족한지는 전부 코드가 미리 정해 뒀다.
그 전 프로젝트였던 StudiON(LangGraph 기반 음원 충돌 분석)도 마찬가지였다. 노드와 엣지를
내가 다 그렸고, LLM은 그 안에서 빈칸을 채웠다.

내가 해 보고 싶었던 건 **LLM이 스스로 다음 행동을 고르는 쪽**이었다. 파일 이름만 보고
판단이 서면 바로 답하고, 애매하면 "내용을 읽어 보겠다"고 스스로 말하는 구조.

## 무엇을 바꿨나

파일 하나마다 에이전트 루프를 새로 돈다. 폴더 전체를 한 루프에 넣지 않은 이유는 두 가지다.
`num_ctx`가 4096이라 파일 서른 개 정보를 한꺼번에 못 담고, 한 파일이 꼬여도 배치가 멈추지
않아야 하기 때문이다.

대신 파일 하나짜리 루프는 **다른 파일을 모른다**는 약점이 있다. 그걸 툴로 메웠다.

| 툴 | 하는 일 |
|---|---|
| `get_file_info` | 크기, 확장자, 수정 날짜 |
| `read_text_content` | 텍스트면 내용 일부 |
| `list_zip_contents` | zip이면 안의 파일 목록 |
| `find_duplicate_files` | SHA-256이 같은 파일 찾기 |
| `find_similar_names` | 이름이 비슷한 파일 찾기 |
| `propose_move` | 최종 답 제출 |

조회 툴 다섯 개는 전부 **인자가 없다.** 지금 처리 중인 파일만 다루는 읽기 전용이다.
LLM이 경로를 지어내서 엉뚱한 폴더를 읽는 일이 아예 불가능하게 만들고 싶었다.

같은 이유로 **LLM에게는 실제 경로를 보여 주지 않는다.** 목적지는 `projects/MQTT`,
`documents` 같은 라벨로만 오간다. 툴이 에러를 뱉을 때도 경로가 새지 않게 막았다.
`C:\FileButlerLab\destinations\projects\MQTT` 같은 문자열은 코드만 안다.

최종 답은 `propose_move` 툴로만 받는다. 그리고 그 제안이 그대로 실행되지는 않는다.
이동 여부는 여전히 코드(`decide_action()`)가 정한다. 이게 이 프로젝트의 원칙이다.
**LLM은 의미를 판단하고, 실제로 벌어지는 일은 코드가 정한다.**

## 예상과 달랐던 것 ①: 4b 모델이 툴 호출을 안 헤맸다

제일 걱정한 부분이었다. 로컬 우선 원칙을 지키려고 `qwen3.5:4b`를 쓰는데(RTX 2060 6GB에
4b면 GPU에 다 올라간다), 이 크기 모델이 툴을 제대로 고를지 자신이 없었다. 툴 이름을
지어내거나, 툴 대신 줄글로 답하거나, 같은 툴을 무한히 부르는 걸 각오했다.

그래서 방어 장치를 깔아 뒀다. 파일당 LLM 호출 6회 제한, 툴 없이 글로 답하면 한 번 재요청,
형식이 틀린 제출은 오류를 돌려주고 재제출 요청.

34개 파일을 돌린 첫 측정 결과다.

| 지표 | 값 |
|---|---|
| 재요청(툴 없이 글로 답함) | **0회** |
| 형식 오류 제출 | **0회** |
| 6회 한도 초과 | **0회** |
| 분류 실패 | **0건** |

방어 장치가 한 번도 발동하지 않았다. 호출 횟수도 2~5회에 고르게 퍼졌다. 파일 성격에 따라
툴을 더 부르거나 덜 부른다는 뜻이다. 이미지처럼 첨부로 바로 보이는 건 2회에 끝내고,
텍스트 파일은 정보를 더 모았다.

툴 사용 빈도를 보면 모델이 나름의 순서를 갖고 있었다.

```
read_text_content   31    get_file_info        20
find_similar_names  26    find_duplicate_files  7
list_zip_contents    2
```

내용을 먼저 읽고, 비슷한 이름을 확인하는 패턴이 많았다. 해시 중복 검사는 7번뿐이었는데,
이건 모델이 "중복일 수도 있겠다"고 의심한 경우에만 불렀다는 뜻이다.

**작은 모델이라 툴 호출을 못 할 거라는 건 내 선입견이었다.** 적어도 툴 6개에 인자가 없는
수준의 단순한 구조에서는 그랬다.

## 예상과 달랐던 것 ②: 정확도가 제자리였다

진짜 예상 밖은 이쪽이었다.

| | 워크플로 | 에이전트 |
|---|---|---|
| 목적지 정확도 | 27/29 | **27/29** |
| 프로젝트 정확도 | 24/29 | **25/29** |

툴을 다섯 개나 쥐여 줬는데 목적지는 한 건도 더 못 맞혔다. 프로젝트가 하나 올랐을 뿐이다.

툴이 실제로 효과를 낸 곳이 없지는 않았다. `old_project_archive_2024.zip`은 워크플로에서
안을 못 봐서 프로젝트를 "없음"으로 찍었는데, 에이전트는 `list_zip_contents`로 안을 열어
`OldProject`를 맞혔다. 툴이 아니면 알 수 없는 정보였다.

그런데 같은 파일에서 목적지는 오히려 틀렸다. zip 안에 프로젝트 문서가 있는 걸 보고
`archives`가 아니라 `projects`로 보내려 했다. **정보가 늘어난 만큼 틀릴 거리도 늘었다.**

비슷한 일이 `report_final_copy.txt`에서도 있었다. `find_similar_names`가
`report_final.txt`를 제대로 찾아냈다. 그런데 모델이 그걸 이렇게 썼다.

> "MarineDashboard 관련 보고서로, report_final.txt와 **유사한 이름의 파일이 inbox에
> 정리되어 있음**"

중복이니 조심하라는 신호로 읽은 게 아니라, **"비슷한 게 저기 있으니 나도 거기로 가자"**는
근거로 썼다. 툴은 정보를 줄 뿐이고, 그 정보를 어떻게 해석할지는 또 다른 문제였다.

이쯤에서 "에이전트로 바꾼 게 의미가 있었나" 싶었다. 의미는 다른 데서 나왔다.

## 로그를 보다가 발견한 것

점수가 같아서 로그를 한 줄씩 봤다. 그러다 이걸 발견했다.

```
분석 중: msvcp140.dll
분류: INSTALLER
목적지: installers
이유: Windows 시스템 DLL 파일로, 프로젝트와 직접적인 관련이 없음.
      설치 파일 카테고리에 적합함.
정책: AUTO_MOVE
[이동 완료] msvcp140.dll
```

`msvcp140.dll`은 Windows 시스템 라이브러리다. 정리 도구가 **절대 건드리면 안 되는 파일**이다.
`nvlddmkm.sys`(NVIDIA 그래픽 드라이버)도 같이 옮겨졌다.

모델의 이유가 묘하다. 시스템 파일이라는 건 알아봤다. 그런데 거기서 **"그러니 건드리면 안 된다"**로
가지 않고 **"그러니 설치 파일 폴더에 어울린다"**로 갔다.

워크플로 버전에서는 같은 파일을 이렇게 판정했다.

```
분류: UNKNOWN
목적지: inbox
이유: dll 파일로 미분류. 프로젝트와 무관함.
정책: KEEP
```

**정보를 덜 받은 쪽이 더 안전하게 판단했다.** 아는 게 없으니 "모르겠다"고 했고, 그래서
건드리지 않았다. 툴로 정보를 더 준 쪽은 "알 것 같다"고 확신했고, 그래서 옮겼다.

## 범인은 7주 전의 나였다

왜 코드가 이걸 안 막았는지 보려고 정책 함수를 열었다.

```python
def decide_action(classification, source) -> MoveAction:
    if classification.target_folder_id == "inbox":
        return "KEEP"

    if classification.requires_confirmation:
        return "ASK_USER"

    if classification.target_folder_id == "projects":
        return "ASK_USER"

    if source.suffix.lower() == ".exe":
        return "ASK_USER"

    return "AUTO_MOVE"        # ← 여기
```

마지막 줄이 `return "AUTO_MOVE"`다. **규칙에 걸리지 않으면 자동 실행**이 기본값이었다.
`.dll`과 `.sys`를 막는 규칙이 없으니 그대로 통과했다.

그런데 더 찝찝한 걸 찾았다. 7주 전에 쓴 설계 문서에 이 얘기가 이미 있었다.

> 같은 이유로 계획의 **`.dll` / `.sys` → `REJECT`도 기각했다.** `msvcp140.dll`과
> `nvlddmkm.sys` 둘 다 모델이 `UNKNOWN` + `inbox`로 정확히 판정했고 정책이 이미 `KEEP`한다.
> **가드를 넣어도 발동만 하고 결과가 바뀌지 않는다.**

가드를 넣으려다 **측정해 보고 뺐다.** 당시 논리는 틀리지 않았다. 실제로 모델이 잘 맞혔고,
안 쓰이는 규칙을 넣는 건 낭비로 보였다. 측정하고 판단한 결과였으니 오히려 모범적이었다.

문제는 그 논리가 **"모델의 답이 고정되어 있다"는 전제 위에** 서 있었다는 거다. 모델을 바꾸거나,
프롬프트를 고치거나, 이번처럼 툴로 입력을 바꾸면 같이 무너진다. 그리고 나는 7주 뒤에 정확히
그 짓을 했다.

워크플로 버전이 그동안 무사했던 것도 **정책이 막아서가 아니라 모델이 알아서 `inbox`라고
답했기 때문**이었다. 같은 구멍이 처음부터 있었고, 드러나지 않았을 뿐이다.

여기서 배운 게 이 글의 핵심이다.

**"지금 모델이 잘 맞히니 가드는 필요 없다"와 "되돌리기 어려운 일은 사람에게 묻는다"는
수명이 다르다.** 앞의 것은 모델이 바뀌면 같이 죽는다. 뒤의 것은 모델이 바뀌어도 산다.

## 고친 방법: 기본값을 뒤집었다

확장자 목록에 `.dll`, `.sys`를 추가하는 건 같은 실수의 반복이다. 다음엔 `.ocx`가 나올 테니까.
대신 **기본값 자체를 뒤집었다.**

```python
AUTO_MOVE_TARGETS = frozenset({"documents", "images"})

    ...
    if classification.target_folder_id in AUTO_MOVE_TARGETS:
        return "AUTO_MOVE"

    return "ASK_USER"        # 기본값이 바뀐 지점
```

"규칙에 안 걸리면 자동 실행"에서 **"허용 목록에 있을 때만 자동 실행"**으로 바꿨다.

그럼 허용 목록에 뭘 넣을까. 여기서 감으로 정하면 또 같은 실수다. 목적지별 정확도를 전수로 셌다.

여기서 한 가지 문제가 있었다. `images` 목적지가 **한 번도 선택된 적이 없었다.** 테스트 파일에
있던 이미지 다섯 장이 전부 아키텍처 다이어그램이나 에러 스크린샷이라 `projects`로 갔기 때문이다.
선택 0건이면 믿을 만한지 아닌지 **잴 근거 자체가 없다.** 그래서 프로젝트와 무관한 일반 사진
네 장을 새로 넣고 다시 측정했다.

| 목적지 | 정확도 | 판정 |
|---|---|---|
| `documents` | **9/9** | 허용 |
| `images` | **8/8** | 허용 |
| `projects` | 38/41 | 이미 확인 받음 |
| `inbox` | 7/8 | 이미 유지 |
| `installers` | **4/6** | 차단 |
| `archives` | **1/2** | 차단 |

경계가 깔끔하게 갈렸다. 그리고 그 경계가 **모델이 받는 입력과 일치했다.**

`documents`는 텍스트라 내용을 읽어서 보낸다. `images`는 사진이 첨부돼 모델이 직접 본다.
둘 다 판단할 재료가 실제로 전달된다. 반면 `installers`와 `archives`로 가는 파일은
`.dll` `.sys` `.dat` `.exe` 같은 것들이라 **파일명과 확장자 말고는 볼 게 없다.**
근거 없이 고르니 틀린다.

틀린 3건의 정답이 전부 `inbox`였다는 것도 의미심장하다. **모델이 틀릴 때는
"건드리면 안 되는 걸 건드리는" 쪽으로 틀렸다.**

## 재측정이 필요 없었던 이유

정책을 바꿨으니 다시 측정해야 한다고 생각했다. 그런데 한 번 더 보니 아니었다.

`decide_action()`은 **순수 함수**다. 분류 결과와 파일 경로만 받고, LLM을 다시 부르지 않는다.
그러니 정책을 바꿔도 **목적지·프로젝트 정확도는 한 글자도 안 바뀐다.** 바뀌는 건
`AUTO_MOVE / ASK_USER / KEEP` 분포뿐이고, 그건 이미 가진 로그에서 계산할 수 있다.

계산해 보니 `AUTO_MOVE` 11 → 9, `ASK_USER` 23 → 25였다.

그래도 한 번 돌려 봤다. 에이전트 버전에는 계산이 못 잡는 2차 효과가 있을 수 있어서다.
자동 이동이 막힌 파일은 inbox에 남는데, 그러면 뒤에 처리되는 파일의 `find_similar_names`
결과가 달라질 수 있다.

결과는 계산과 정확히 일치했고(9 / 25 / 3), 2차 효과는 없었다. 분류 정확도도 그대로였다.

**그래도 돌려 보길 잘했다.** 안 돌렸으면 "아마 괜찮을 것"으로 남았을 거다.
"논리적으로 이러니 괜찮다"와 "돌려 보니 괜찮았다"는 다른 문장이다.

최종 결과는 이렇다.

- 관찰된 잘못된 자동 이동 3건을 **전부 막았다**
- 올바른 자동 이동은 **하나도 잃지 않았다**
- 비용은 실행당 확인 2건 늘어난 것

## 정리하면

에이전트로 바꿔서 **정확도는 안 올랐다.** 27/29 그대로다.

대신 **숨어 있던 설계 결함이 드러났다.** 그리고 그 결함은 에이전트 때문에 생긴 게 아니라,
처음부터 있었는데 운 좋게 안 터지고 있던 거였다.

생각해 보면 이게 더 쓸모 있는 결과다. 점수가 올랐으면 "에이전트가 좋다"는 결론으로 끝났을 거다.
점수가 그대로였기 때문에 로그를 한 줄씩 읽었고, 그러다 7주 전의 판단이 틀렸다는 걸 알았다.

**측정은 잘된 걸 확인하는 도구가 아니라, 틀린 걸 드러내는 도구다.** 그리고 에이전트로 바꾼 건
이 시스템에 가한 가장 효과적인 스트레스 테스트였다.

1. **중복 파일 처리.** `find_duplicate_files`가 중복을 찾아도 모델이 "조심하라"가 아니라
   "거기로 보내라"로 해석한다. 애초에 중복을 보낼 `quarantine`이 아직 없어서 생긴 문제이기도 하다.
2. **경계 사례 이미지.** 새로 넣은 사진 네 장은 전부 풍경·사물이라 쉬운 쪽이었다.
   화이트보드를 찍은 사진처럼 **사진이면서 프로젝트 자료**인 경우는 아직 안 쟀다.
3. **이미 정리된 폴더.** 측정할 때마다 목적지를 비우고 시작하는데, 실제로 쓸 때는
   이미 정리된 파일이 쌓여 있다. 그 상태에서 중복 탐지가 어떻게 되는지는 미측정이다.

그리고 다음 빌드로그 주제는 **이 툴들을 MCP 서버로 분리하는 것**이다. 지금은 툴 다섯 개가
에이전트 스크립트 안에 들어 있는데, 이걸 밖으로 빼면 다른 에이전트도 같은 툴을 쓸 수 있다.

> [빌드로그 #2](/posts/filebutler-agent-tool-calling/) 마지막에 "다음은 이 툴들을 MCP
> 서버로 분리하는 것"이라고 썼다. 분리 자체는 하루면 끝났다. 정작 오래 걸린 건
> **그 분리가 아무것도 망가뜨리지 않았다는 걸 증명하는 일**이었다.

## MCP가 뭔지부터

솔직히 나도 이번에 처음 제대로 봤다. 한 줄로 쓰면 **LLM 애플리케이션이 외부 도구에
접근하는 방식을 표준화한 통신 규약**이다.

도구를 쓰는 AI 앱이 3개이고 붙일 도구가 4개면, 연결 코드를 3 × 4 = 12개 짜야 한다.
가운데 공통 규약을 끼우면 3 + 4 = 7개로 준다. USB-C에 비유하는 설명을 많이 쓴다.

역할이 셋인데 이게 헷갈렸다.

| 역할 | 무엇인가 | FileButler로 치면 |
|---|---|---|
| **Host** | 사용자가 쓰는 앱. LLM을 부르고 흐름을 통제한다 | 기존 에이전트 루프 |
| **Client** | 호스트 안의 연결 담당자. 서버 하나당 하나 | SDK가 만들어 준다 |
| **Server** | 도구를 내놓는 쪽 | 새로 만든 `filebutler-mcp` |

여기서 내가 제일 오해했던 것 하나.

> **LLM은 MCP를 모른다.**

`qwen3.5:4b`도, Claude도 MCP를 직접 말하지 않는다. MCP는 **호스트와 서버 사이의**
규약이고, 모델은 그 사이에 끼어 있지 않다. 호스트가 서버에 "무슨 툴 있어?"(`tools/list`)를
묻고, 받은 걸 모델이 아는 형식으로 **번역해서** 넘긴다. 모델이 툴을 고르면 호스트가
다시 서버에 실행을 시킨다(`tools/call`).

그러니까 빌드로그 #2에서 만든 에이전트 루프가 이미 이 구조였다. 다만 3~7번에서
서버를 거치지 않고 파이썬 함수를 직접 불렀을 뿐이다. **MCP로 바꾼다는 건 그
함수 호출 자리에 프로세스 경계를 넣는 것**이다.

## 무엇을 빼고 무엇을 남겼나

조회 툴 5개(`get_file_info`, `read_text_content`, `list_zip_contents`,
`find_duplicate_files`, `find_similar_names`)만 서버로 뺐다. **파일을 실제로 옮기는
코드는 호스트에 남겼다.**

`apply_move` 같은 툴을 서버에 두는 선택지도 있었다. 그러면 Claude Desktop에 붙이는
것만으로 정리 기능 전체를 쓸 수 있다. 안 한 이유는 **undo가 아직 없어서**다. 잘못
옮겼을 때 되돌릴 수단이 없는 상태에서 실행 권한을 프로세스 밖으로 공개하는 건 이르다.

`propose_move`(최종 답 제출)도 서버에 안 뒀다. 이건 바깥세상을 조회하는 일이 아니라
**"대화를 끝내겠다"는 신호**다. 루프를 끝낼지 정하는 건 호스트의 일이다.

## 인자 없는 툴 vs 무상태 프로토콜

여기서 설계 문제가 하나 터졌다.

빌드로그 #2에서 조회 툴 5개는 **전부 인자가 없게** 만들었다. "지금 분류 중인 파일"만
다루게 해서 모델이 임의 경로를 건드릴 길을 막은 거다. 4b 모델이 툴 호출을 한 번도
안 틀린 이유 중 하나로도 보인다 — 고를 게 이름뿐이고 채울 인자가 없으니까.

그런데 서버는 별도 프로세스다. "현재 파일"을 모른다.

```
호스트: "read_text_content 실행해 줘"
서버:   "...어느 파일을?"
```

처음 떠올린 건 서버가 `set_current_file`로 상태를 들고, 호스트별로 락을 거는 거였다.
**명세가 이걸 금지한다.**

> Servers **MUST NOT** rely on prior requests over the same connection to establish
> context. (…) an open connection, such as a STDIO process, **is not a conversation or
> session**: clients may interleave unrelated requests on the same transport.

프로세스 하나 = 호스트 하나는 맞지만, **그 호스트가 한 프로세스에 서로 무관한 요청을
섞어 보낼 수 있다.** 지금은 파일을 하나씩 처리하지만 나중에 병렬로 돌리고 싶어지면
바로 무너진다. 락을 걸면 병렬이 막히고, 안 걸면 파일이 섞인다.

그런데 명세가 답도 준다.

> State that needs to span multiple requests **MUST** be referenced by an explicit
> identifier the client passes on each request.

매 요청에 식별자를 실어 보내라는 것. 그래서 **스키마를 두 겹으로** 뒀다.

| | 모델이 보는 것 | 서버가 받는 것 |
|---|---|---|
| `read_text_content` | 인자 없음 | `{"filename": "..."}` |

모델이 인자 없이 툴을 부르면, **호스트가** 현재 파일명을 끼워 `tools/call`을 보낸다.
모델은 파일명을 만들지 않으니 경로를 지어낼 길이 없고, 서버는 무상태로 남는다.

이게 가능한 이유는 **호스트가 모델에게 보여 줄 툴 정의를 직접 만들기 때문**이다.
서버에서 받은 정의를 그대로 넘길 의무가 없다. 그 사이를 메우는 게 호스트의 일이다.

## 그리고 검증에서 막혔다

계획은 단순했다. 전환 후 다시 측정해서 전과 같으면 성공.

**달랐다.** 파일 38개 중 툴 호출 순서 9개, 최종 판정 5개가 바뀌었다.

| | 분리 전 | 분리 후 |
|---|---|---|
| 목적지 정확도 | 27/29 | 26/29 |
| 프로젝트 정확도 | 25/29 | 27/29 |

오류는 양쪽 0건. 하나는 내려가고 하나는 올라갔다. 버그라면 한 방향으로 망가지지
이렇게 섞이지 않는다. 그래도 원인은 찾아야 했다.

하나씩 지웠다. 툴 목록 **순서** — 같음. 툴 **설명** — 바이트 단위로 같음. 그런데
이건 내 로컬 상수를 비교한 거라, 실제로 네트워크를 타고 오는 값도 따로 떠서 비교했다
— 역시 같음. 시스템 프롬프트, 재요청 문구, 모델 이름, enum, 등록된 프로젝트 목록,
파일 처리 순서 — 전부 같음.

그래서 추측을 멈추고 **모델에게 실제로 가는 인자를 통째로 떠서** 비교했다.

> 완전히 동일.

같은 입력인데 다른 출력이 나왔다. 여기서 한참 헤맸다.

## 틀린 건 전제였다

의심할 걸 다 의심하고 나서야 깨달았다. 내가 깔고 있던 전제가 있었다.

> **같은 코드로 다시 돌리면 항상 같은 결과가 나온다.**

이게 성립해야 "다르면 코드 탓"이라고 말할 수 있다. 그리고 나는 **이 전제를 한 번도
확인한 적이 없었다.**

같은 코드로 한 번 더 돌려 봤다. 판정은 같았지만 툴 호출이 한 건 달랐다. 나중에 같은
파일을 또 돌리니 또 달랐다. `temperature=0`인데도 그렇다. 로컬 모델은 완전히
결정적이지 않고, **판단이 반반인 경계 파일**에서 그 흔들림이 겉으로 드러난다.

우리 fixture에서 흔들리는 건 `backup_2026Q2.dat` 하나였다. `.dat`라 내용을 못 읽고
비슷한 이름도 없어서, 모델이 "더 조회할까 말까"에서 거의 50:50인 상태다. 공교롭게도
분리 전후가 처음 갈라진 지점도 그 파일이었다.

**즉 실행 결과 비교로는 "코드가 바꾼 것"과 "모델이 흔들린 것"을 구분할 수 없다.**

내가 전에 "재실행해서 같으면 안 바뀐 것"이라고 자신 있게 말할 수 있었던 건, 비교한
두 실행이 시간적으로 붙어 있어 모델 상태가 같았기 때문이었다. 운이었다.

## 그래서 출력 말고 입력을 비교했다

생각해 보면 리팩터링이 주장하는 건 애초에 **"모델이 같은 답을 낸다"가 아니다.**
**"모델이 보는 것이 똑같다"**이다. 앞의 것은 모델의 변덕까지 검증 대상에 끌어들이고,
뒤의 것은 내 코드만 본다.

그래서 작은 스크립트를 하나 만들었다. 파일마다 두 가지를 뜬다.

1. **첫 요청** — 시스템 프롬프트, 첫 사용자 메시지(이미지 첨부 여부), 툴 목록 전체
2. **모든 툴의 결과** — 조회 툴 5개를 전부 실행한 값

둘을 합치면 모델이 그 파일에 대해 볼 수 있는 게 전부 들어간다. **모델을 부르지 않으니
결정적이고 몇 초면 끝난다.**

분리 전 코드와 분리 후 코드로 각각 떠서 비교했다.

> **38개 파일 전부 바이트 단위로 동일.**

이제야 "MCP 분리가 모델이 보는 걸 아무것도 안 바꿨다"고 말할 수 있게 됐다.

여기서 배운 걸 정리하면 이렇다.

- **리팩터링 검증** → 입력을 비교한다. 결정적이고 빠르다.
- **동작을 의도적으로 바꾸는 실험**(프롬프트·툴 설명·모델 교체) → 입력이 달라지는 게
  목적이니 여러 번 돌려 분포를 본다.
- 그리고 **측정 도구 자체를 먼저 재야 한다.** 내 저장소 규칙이 "측정 먼저"인데,
  정작 측정 방법이 유효한지를 안 쟀다.

## 진짜로 바뀐 건 신뢰 경계였다

분리가 끝나고 보니 성능은 그대로였다. 그럼 뭐가 바뀐 거지?

코드를 다시 보다가 알았다. 서버에 이런 함수가 생겨 있었다.

```python
def resolve_lab_file(filename: str) -> Path:
    """파일명을 inbox 안의 실제 경로로 바꾼다. 랩 밖이면 거부한다."""
```

**리팩터링 전에는 없던 코드다.** 툴이 프로세스 안에만 있을 때는 필요가 없었다.
파일명을 넣는 게 내 코드였으니까.

그런데 서버가 되는 순간, **부르는 쪽이 누구인지 서버는 모른다.** 내 호스트는 파일명을
직접 끼워 넣지만, 다른 호스트에서는 **모델이 파일명을 만들어 넣는다.** 그러면
`../../Windows/win.ini` 같은 게 들어올 수 있다.

MCP에는 `readOnlyHint` 같은 툴 주석도 있다. 그런데 이건 **힌트이지 보증이 아니다.**
호스트 UI가 참고할 뿐이고, 서버가 거짓으로 달 수도 있다. 안전장치로 쓰면 안 된다.
진짜 방어는 이 서버에 이동 툴이 아예 없다는 사실과, 위 경계 검사다.

**이게 이번 작업의 실질이다.** 코드를 옮긴 게 아니라, 신뢰 경계가 프로세스 밖으로
옮겨갔고 그래서 없던 방어가 필요해진 것이다.

## 리뷰에서 나온, 생각도 못 한 구멍

전용 코드 리뷰 에이전트를 돌렸다. P1(최상위)은 없었지만 P2가 3건 나왔고, 그중 하나는
내가 "다 막았다"고 믿던 곳이었다.

내 경계 검사는 이 순서였다.

```python
resolved = candidate.resolve()        # 1) 경로를 펼치고
if not resolved.is_relative_to(inbox):  # 2) 랩 안인지 본다
    raise LabBoundaryError(...)
```

이 순서 덕분에 심볼릭 링크도 `..`도 Windows 후행 공백 트릭도 다 막힌다. 실제로
리뷰어가 `NUL`, `CON`, `COM1`, 드라이브 상대 경로까지 다 넣어 보고 확인해 줬다.

문제는 **1번에 부작용이 있다**는 거였다.

```
'//10.255.255.1/share/x.txt'  ->  거부됨.  단 21.04초 걸림
```

Windows에서 UNC 경로를 `resolve()`하면 **실제로 SMB 접속을 시도한다.** 경계 검사는
그 뒤에 돈다. 즉 **막기는 하는데, 막기 전에 이미 나갔다.**

모델이 파일명을 만드는 호스트에서 `\\attacker.example.com\s\x`가 들어오면, 서버가
그 호스트로 NTLM 인증을 시도한다. Windows 해시 유출의 고전적 경로다. 그리고 그
트리거는 **모델이 방금 읽은 파일 내용 안의 지시문**일 수 있다.

고치는 건 간단했다. 파일시스템을 건드리기 전에 문자열로 먼저 거른다.

```
닿지 않는 UNC 거부:  21.04초  →  0.00초
```

기존 검사는 지우지 않고 2차 방어선으로 남겼다. 구문 검사만으로는 심볼릭 링크를
못 잡고, 경계 검사만으로는 이 부작용을 못 막는다. **둘 다 필요하다.**

여기서도 교훈이 하나. 나는 "막았는가"만 봤고, **"막기 전에 무슨 일이 일어나는가"**는
안 봤다.

## 그래서 진짜 다른 호스트가 쓸 수 있나

"재사용 가능해진다"가 이번 작업의 전부인데, 분리만 해서는 **가능성일 뿐**이다.
실제로 붙여 봤다.

저장소에 `.mcp.json`을 넣고 새 Claude Code 세션을 띄웠다. 완전히 별개의 호스트이고,
모델도 `qwen3.5:4b`가 아니라 Claude다. 시켰더니 이렇게 답했다.

> `report_final_copy.txt`의 내용은 같은 inbox에 있는 `report_final.txt`와 완전히
> 같습니다(중복 1건). 사용한 툴: `mcp__filebutler__find_duplicate_files`

내 에이전트 스크립트를 전혀 거치지 않았다. 이제 주장이 아니라 사실이다.

그리고 이 세션에서는 **모델이 파일명을 직접 넣어야 했다.** 두 겹 스키마를 만든 이유가
여기서 실제로 확인됐다. 경로 탈출도 넣어 봤다.

| 넣은 값 | 결과 |
|---|---|
| `report_final_copy.txt` | 허용 |
| `../../Windows/win.ini` | 거부 |
| `..\..\..\Users\<나>\.ssh\id_rsa` | 거부 |
| `C:/Windows/win.ini` | 거부 |

## 정리하면

| 항목 | 변화 |
|---|---|
| 모델이 보는 입력 | 안 바뀜 (38개 파일 바이트 동일) |
| 분류 성능 | 안 바뀜 |
| 툴 호출 속도 | 190회에 3.3초 → 7.0초 (실행당 약 2초, 무시 가능) |
| 다른 호스트의 사용 | **가능해짐** |
| 신뢰 경계 | **프로세스 밖으로 이동** |
| 테스트 | 74개 → 117개 |

속도가 느려진 이유도 설명된다. 전에는 파일 목록과 해시를 실행 내내 캐시했는데,
**무상태 서버는 호출마다 랩을 다시 훑는다.** 명세를 지키는 대가다.

이번 작업에서 제일 오래 붙들고 있었던 건 MCP 자체가 아니라 **"안 바뀌었다를 어떻게
증명하나"**였다. LLM을 끼고 일하면 출력이 흔들리니까, 평소 쓰던 "돌려 보고 같으면 됨"이
그대로는 안 먹힌다. 그럴 땐 **검증 대상을 출력에서 입력으로 한 칸 당기면** 된다는 게
이번에 건진 것이다.

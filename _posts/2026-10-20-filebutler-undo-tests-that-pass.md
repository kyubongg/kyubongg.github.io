## 만들던 도구가 없어서 손으로 수습했다

작업 중간에 사고가 났다.

구현을 맡긴 서브에이전트가 "이 테스트가 정말 실패하는지" 확인하려고 수정을 잠깐 되돌린 채 테스트를 돌렸다. 그 테스트는 `organize_inbox.py`를 실제로 실행해 보는 것이었다. 수정이 없는 상태였으니 **진짜 파일 정리 작업이 진짜 `C:\FileButlerLab` 폴더에 대고 75초간 돌았다.**

에이전트는 "`ls`로 확인해 보니 파일이 그대로 있다"고 보고했다. 그 확인이 틀렸다.

```
$ find destinations -newermt "2026-10-19 00:00"
(없음)
```

`shutil.move`는 **파일의 수정 시각을 그대로 가져간다.** 그래서 오늘 옮겨진 파일도 8월 17일자로 보인다. 수정 시각 말고 **변경 시각(ctime)**으로 봐야 한다.

```
$ find destinations -newerct "2026-10-19 00:00"
documents/문서1.txt
documents/카페_영수증_2026-08-15.txt
```

두 개가 실제로 옮겨져 있었다. 둘 다 `documents`로 가는 파일이라 확인 없이 자동 이동되는 대상이었다. 예측대로 움직인 것이다.

그리고 **되돌릴 방법이 없었다.** 그게 그날 내가 만들고 있던 기능이었다.

## 무엇을 만들었나

파일을 옮길 때마다 기록을 남기고, 나중에 그 이동을 되돌린다.

```powershell
uv run python scripts\undo.py              # 마지막 실행 전체를 되돌린다
uv run python scripts\undo.py <원래 파일명>  # 그 파일만 되돌린다
```

기록은 `operations.jsonl`에 한 줄씩 쌓인다. 설계에서 하나만 꼽으면 **기존 줄을 절대 고치지 않는다**는 것이다.

원래 계획은 되돌릴 때 그 줄의 `undo_status`를 `AVAILABLE`에서 `DONE`으로 **고치는** 방식이었다. 그만뒀다. 파일 가운데 한 줄을 고치려면 파일 전체를 다시 써야 하는데, 그 도중에 프로그램이 죽으면 기록 전체가 날아간다. **되돌리기용 기록 파일이 사고의 원인이 되는 셈이다.** 대신 "되돌렸다"는 줄을 맨 뒤에 새로 붙인다. 쓸 때는 뒤에 붙이기만 하고, 읽을 때 뒤에서부터 훑는다.

여기까지는 설계 이야기고, 이 글에서 하려는 건 다른 이야기다.

## 통과하는데 아무것도 안 막는 테스트, 다섯 가지

작업을 7개로 쪼개고 각 작업마다 **다른 리뷰어**를 붙였다. 리뷰가 중요한 지적을 17건 찾아냈다. 다 끝나고 보니 **거의 전부 같은 종류의 문제였다.**

테스트를 돌릴 때와 실제로 프로그램을 쓸 때는 조건이 다르다. 그래서 **테스트가 전부 통과해도 버그가 그대로 남아 있을 수 있다.** 어떻게 그럴 수 있는지 다섯 가지 경우가 나왔다.

### 1. 테스트와 실제 실행이 서로 다른 복사본을 본다

두 스크립트에 똑같이 복사돼 있던 코드를 `batch.py` 하나로 합쳤다. 테스트 123개가 통과했다.

리뷰어가 이걸 짚었다. `python scripts\organize_inbox.py`로 실행하면 파이썬은 그 파일을 **`__main__`이라는 이름으로** 메모리에 올린다. `organize_inbox`라는 이름으로는 올라가 있지 않다. 그 상태에서 `batch.py`가 `from organize_inbox import ...`를 하면, 파이썬은 "그런 이름 없는데?" 하고 **같은 파일을 처음부터 한 번 더 실행한다.**

```
__main__          LAB_ROOT, TARGET_FOLDERS   (복사본 A)
organize_inbox    LAB_ROOT, TARGET_FOLDERS   (복사본 B)
```

그래서 `main()`은 복사본 A의 설정을 보고, 파일을 옮기는 코드는 복사본 B의 설정을 본다. 지금은 두 값이 같으니 아무 일도 안 일어난다.

**테스트가 왜 이걸 못 잡느냐가 중요하다.** 테스트는 복사본 B의 설정을 바꿔치기해서 임시 폴더를 쓰게 만드는데, 테스트에서는 복사본이 **하나밖에 없다.** 복사본이 둘로 갈라지는 건 명령줄에서 직접 실행할 때뿐이다. 테스트는 그 상황을 아예 만들지 않는다.

파일을 옮기는 프로그램에서 "어느 폴더를 쓸지"를 담은 설정이 두 벌로 존재하는 건, 지금 멀쩡해 보여도 고쳐야 할 문제다.

### 2. 테스트가 그 코드까지 가지도 못한다

파일을 옮긴 뒤 "같은 내용이 제대로 도착했는지" SHA-256 해시로 확인하는 코드를 넣었다. 실패하는 경우를 확인하는 테스트도 같이 썼다. 리뷰어가 확인해 봤다.

> 해시를 비교하는 줄을 통째로 지워도 테스트 128개가 전부 통과한다.

내가 쓴 테스트는 "파일 옮기기"를 아무것도 안 하는 가짜로 바꿔치기해서 실패를 만들었다. 그러면 **원본 파일이 제자리에 그대로 남아 있다.** 검사 순서가 "원본이 사라졌나? → 목적지에 생겼나? → 내용이 같나?"인데, 첫 번째에서 이미 걸린다. 해시 비교하는 줄까지 가지도 않는다.

제대로 테스트하려면 **원본은 지우고 목적지에는 엉뚱한 내용을 쓰는** 가짜가 필요하다. 그래야 앞의 두 검사를 통과하고 해시 검사에서만 걸린다.

### 3. 안전장치 목록에 새 항목을 빠뜨렸다

테스트가 실수로 진짜 폴더를 건드리지 않도록, 테스트 시작할 때 경로 설정을 전부 임시 폴더로 바꿔치기하는 코드가 있다. 거기 이렇게 적혀 있다.

> 하나라도 빠뜨리면 테스트가 진짜 `C:\FileButlerLab`을 건드린다.

이번에 기록 파일 경로를 새로 추가했다.

```python
HISTORY_PATH = LAB_ROOT / "history" / "operations.jsonl"
```

이 값은 **프로그램이 시작할 때 딱 한 번 계산된다.** 테스트가 나중에 `LAB_ROOT`를 임시 폴더로 바꿔도, `HISTORY_PATH`에는 이미 계산이 끝난 진짜 경로가 들어 있다. 그대로 뒀으면 **기록 테스트가 진짜 폴더에 파일을 썼을 것이다.**

안전장치를 만들어 놓고 새 항목을 거기 등록하지 않으면, 위에 적어 둔 저 문장이 사실이 아니게 된다.

### 4. 지워도 아무도 모르는 안전장치

되돌리기는 기록 파일에 적힌 경로로 파일을 옮긴다. 그런데 **그 파일은 사용자가 메모장으로 열어서 고칠 수 있다.** 그래서 경로를 믿지 않고 세 단계로 검사한다. 마지막 단계는 심볼릭 링크로 폴더 밖을 가리키는 경우를 잡는 **유일한** 검사고, 코드에도 "앞 단계만으로는 링크를 못 잡는다"고 적어 뒀다.

리뷰어가 테스트 20개를 하나씩 그 검사에 대조해 봤다. **그 두 줄을 지워도 20개가 전부 통과했다.** 링크를 만들어서 시험하는 테스트가 하나도 없었기 때문이다.

기록에 `C:\FileButlerLab\destinations\documents\x.md`라고 적혀 있는데 그 `documents`가 사실은 `C:\Users\bong\Documents`로 연결된 링크라면, 그 두 줄만이 **사용자의 진짜 문서가 옮겨지는 걸** 막는다. 아무 테스트도 안 걸려 있으면 누가 나중에 정리하다가 지워도 아무도 모른다.

### 5. 테스트가 쓴 입력이 현실적이지 않았다

마지막은 전체 리뷰에서 나왔고, 이게 제일 아팠다.

```python
open(path, encoding="utf-8")   # 기록을 읽는 유일한 통로
```

파이썬은 파일을 읽으면서 글자를 하나씩 해석한다. 그런데 UTF-8에서 한글 한 글자는 **3바이트**다. 파일이 그 3바이트 중간에서 끝나 있으면, 마지막에 "글자가 덜 왔는데요" 하면서 오류를 낸다. 그걸 아무도 잡지 않아서, 되돌리기를 실행한 사용자는 **오류 메시지 더미만 보게 된다. 되돌리기가 통째로 안 된다.**

언제 그런 파일이 생기냐면, **기록을 쓰는 도중에 전원이 나갔을 때**다. 내 설계 문서에 "그런 줄은 건너뛰고 나머지는 전부 읽혀야 한다"고 **직접 써 둔** 상황이다.

테스트도 있었다.

```python
path.write_text('{"type":"MOVE"}\n{"type":"MO', ...)
```

**영어만 잘랐다.** 영어는 한 글자가 1바이트라 중간에서 잘릴 일이 없다. 그런데 이 프로그램의 기록은 대부분 한글 파일명이 들어간다. 실제로는 한글 중간에서 잘릴 확률이 훨씬 높다.

테스트가 있었고, 통과했고, 아무것도 막지 못했다.

## 다섯 가지의 공통점

"테스트가 없다"가 아니다. **테스트가 있는데 그 코드를 지나가지 않는다**는 것이다. 그리고 그건 테스트 코드를 읽어서는 잘 안 보인다.

그래서 중간부터 수정 지시에 한 줄을 넣기 시작했다.

> 그 코드를 잠깐 지우거나 바꿔 보고, **새 테스트가 실제로 실패하는지** 확인한 다음 원래대로 돌려놔라.

효과가 바로 나타났다. 한 구현자는 해시 비교 줄을 지운 뒤 "새 테스트 하나만 실패(1 failed, 19 passed)"를 확인해서 보고했다. 다른 구현자는 경계 검사 두 줄을 지우고 **"정확히 그 한 건만"** 실패하는 걸 보여줬다.

"정확히 한 건"이라는 게 중요하다. 여러 개가 같이 실패하면 그 코드가 다른 데서도 쓰인다는 뜻이고, 하나도 실패하지 않으면 그 테스트는 애초에 그 코드를 안 보고 있다는 뜻이다.

나중에는 시키지 않은 곳까지 스스로 이 확인을 하는 구현자도 나왔다.

## 내가 쓴 설계 문서가 세 번 틀렸다

코드만 문제가 아니었다. 설계 문서를 먼저 쓰고 구현했는데, 그중 세 군데가 틀렸거나 빠져 있다는 게 드러났다. **코드가 아니라 문서를 고쳤다.**

제일 뼈아픈 건 한국어 한 문장이었다.

> 파일명을 지정한 경우 → 그 이름의 **가장 최근 이동 중 아직 안 되돌린 것**

구현자는 "안 되돌린 것들 중에서 가장 최근 것"으로 읽었다. 리뷰어는 "가장 최근 것, 단 아직 안 되돌렸을 때만"으로 읽었다. **둘 다 문법적으로 맞는 해석인데 동작이 전혀 다르다.**

앞쪽으로 읽으면 이런 일이 생긴다. 같은 이름의 파일이 예전에 한 번, 최근에 한 번 옮겨졌다고 하자. 최근 것을 되돌리고, 정리를 다시 돌리고, 또 되돌리기를 치면 — **몇 달 전에 옮긴 파일이 조용히 돌아온다.** 안전 검사 네 개가 하나도 이걸 못 막는다. 전부 통과한다. 파일도 멀쩡하고 해시도 맞으니까. 틀린 건 동작이 아니라 **사용자의 의도**다.

나머지 둘은 "판정하는 시점과 실제로 옮기는 시점 사이에 틈이 있다"는 걸 안 적은 것, 그리고 "깨진 줄"을 JSON 문법 오류로만 정의해서 **구현자가 문서를 정확히 따랐는데도 요구가 충족되지 않은** 것이다. 위의 5번이 거기서 나왔다.

## 왜 잡혔나

작업마다 **다른 리뷰어**를 붙인 게 컸다. 혼자 구현하고 혼자 검토했다면 자기가 쓴 테스트를 믿고 넘어갔을 것들이다. 실제로 구현자들은 "안전하다"고 보고했고, 그중 하나는 리뷰어가 반박해서 뒤집혔다.

비용은 든다. 작업마다, 리뷰마다 처음부터 맥락을 다시 읽어야 한다. 그리고 **각 리뷰어는 자기가 맡은 변경분만 본다.** 그래서 "앞 작업에서 고친 걸 뒤 작업이 되돌려놨는지"는 아무도 못 본다. 그건 마지막에 전체를 보는 리뷰가 따로 해야 한다.

실제로 병합 직전 리뷰에서 둘이 더 나왔는데, 둘 다 **이미 고친 자리 바로 옆**이었다.

- 예외를 던지는 대신 "검증 실패"를 값으로 돌려주도록 고쳐 놓고, **그 아래 해시 계산이 예외를 다시 던질 수 있게 열려 있었다**
- 파일 크기 확인을 `try` 안으로 옮겨서 배치가 중단되는 걸 막고 **"왜 `try` 안이어야 하는지" 주석까지 달아 놨는데, 두 줄 위의 `print`가 여전히 밖에 있었다**

두 번째는 주석이 경고한 바로 그 문제가 주석 두 줄 위에 그대로 남아 있던 셈이다.

## 숫자

```
테스트         117개 → 213개
리뷰 지적      중요 17건 + 심각 1건, 전부 수정
사소한 지적    36건 중 6건을 "병합 전 필수"로 분류
커밋          21개

실제 폴더에서 1회 검증
  38개 파일 처리, 9개 이동, 기록 38건 = 파일 하나당 정확히 한 줄
  되돌리기 → 9개 전부 원래 이름으로 복귀, 거부 0, 실패 0
  최종 상태 = 처음 초기화했을 때와 동일
```

마지막 확인이 제일 마음에 들었다. 되돌린 **직후에 한 번 더** 되돌리기를 쳐 봤다.

```
되돌릴 것이 없습니다: 마지막 실행 run-20261020-210241
```

방금 끝난 되돌리기 작업을 "마지막 실행"으로 착각하지 않고 그 앞의 정리 작업을 가리켰고, 거기 되돌릴 게 없자 **더 이전 작업까지 거슬러 올라가지 않고 끝냈다.** 리뷰가 잡아서 고친 두 가지가 함께 작동한 결과다. 그중 하나를 안 고쳤다면 여기서 되돌리기가 영영 안 되는 상태가 됐을 것이다.

## 정리

되돌리기를 만들면서 배운 건 되돌리기에 대한 게 아니었다.

**"테스트를 추가했다"와 "그 코드가 테스트로 지켜진다"는 다른 말이다.** 그 차이는 테스트를 읽어서는 잘 안 보이고, 그 코드를 일부러 망가뜨려 보면 바로 보인다.

이번에 나온 다섯 가지는 전부 통과하는 테스트였다. 테스트와 실행이 서로 다른 복사본을 보고 있었고, 테스트가 그 코드까지 가지도 못했고, 안전장치 목록에 새 항목이 빠져 있었고, 지워도 아무도 모르는 검사가 있었고, 테스트가 쓴 입력이 현실적이지 않았다.

사용자 파일을 직접 옮기는 프로그램이라면, 한 번씩 망가뜨려 보고 확인할 값이 있다.
